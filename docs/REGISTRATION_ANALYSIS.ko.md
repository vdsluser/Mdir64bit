# 등록 로직 복원과 등록판 실행 조사

조사일: 2026-10-21. 원본은 보존하며 별도 작업 복사본과 FAT 이미지에서 분석한다. 이 문서는 이전의 ‘등록판 제한으로 미검증’ 결과를 보완한다. 모든 등록판 기능의 검증 완료를 의미하지 않는다.

## 목적과 접근

원본 MSET의 등록 입력·검증·MDIR.REG 생성 절차를 조사하고, 새 합성 이름과 비밀번호로 등록번호를 생성하여 원본이 받아들이는지 확인한다. 실행 파일의 분기 패치나 등록 검사 제거는 사용하지 않는다. 원본 바이너리·개인 이름·동봉 등록정보·메모리 덤프는 공개하지 않는다.

로컬 `serial.txt`에는 후보 두 세트가 있었다. 두 후보의 체크섬을 복원 코드와 비교했으며 원문은 공개하지 않았다. 두 번째 후보로 등록 파일이 변경되어 원본 등록 절차의 기준 사례를 확보했다. 새 번호 생성 검증은 이 후보를 그대로 배포하는 것과 구분한다.

## 복원한 MSET 검사

분석 대상은 이 저장소 인벤토리의 MSET.EXE 3.10이다. MZ 실행부의 복호화/전개 이후 메모리를 64KiB 세그먼트별로 읽고 16비트 x86 명령을 분석했다. DOS 실모드 메모리 덤프에서 오프셋이 64KiB를 넘어가면 같은 세그먼트가 반복되는 점을 확인해, 전체 덤프는 세그먼트를 바꾸어 결합했다.

해당 실행의 MSET 등록 루틴은 `CS:2D31`에서 시작했다. 문자열 전처리와 체크섬은 별도 단위의 함수로 호출된다. 실제 세그먼트 값은 로딩 위치에 따라 바뀌므로 영구 파일 오프셋으로 사용하면 안 된다.

확인한 정상 경로의 검사:

1. 영문 이름과 비밀번호에서 ASCII 공백 `0x20`을 제거한다. 대소문자 변환은 이 경로에서 하지 않는다.
2. 정규화된 이름 뒤에 비밀번호를 붙여 16비트 체크섬을 계산한다.
3. 등록번호는 길이 19, 형식 `25xx-xxxx-xxxx-xxxx`를 검사한다.
4. 번호의 **1기반 3·6·8·11·13번째 문자**를 이어 붙인 십진값을 체크섬과 비교한다.
5. **1기반 4·7·9·12·14번째 문자**로 보조 값을 만들며, 8개의 번호 쌍과 이름 지문을 이용하는 거부 목록도 검사한다.
6. 최종 네 자리는 입력 대화상자의 체크섬에는 쓰이지 않지만, **등록 파일 생성 단계의 추가 검사**에 필요하다. 네 개의 십진 그룹 합계를 `S`라 할 때 `(S mod 9645) mod 1000 = 154`를 만족해야 한다.
7. 체크섬이 0인 경우 성공 값으로 사용할 수 없어 생성기에서 거부한다.

체크섬 의사 코드:

```text
table[0] = 0xCFA2
for i = 1..255:
    table[i] = table[i-1] XOR (5*i)

state = 0xCF9E
for i, byte in input_bytes (i starts at 1):
    state = (state XOR 0xCD1A XOR
             ((table[byte] << ((i mod 8)+1)) AND 0xFFFF)) AND 0xFFFF
    table[byte] = state
return state
```

구현은 [registration_key.py](../tools/analysis/registration_key.py)다. 원본이 요구하는 영문 이름 범위를 우선해 출력 가능한 ASCII만 지원한다. Pascal short string의 합계 255바이트를 넘는 입력을 거부하며, 거부 목록의 번호 쌍은 보수적으로 회피한다. 전체 거부 목록의 이름 지문 함수를 복제할 필요 없이 충돌하는 번호 쌍 자체를 선택하지 않는다.

## 생성기 사용

저장소 루트에서:

```powershell
python tools/analysis/registration_key.py --name "MDIR64BIT RESEARCH" --password 2026
```

이 합성 입력의 생성 번호는 `2560-4080-8040-0119`이다. 원본 MSET의 **등록판생성**에서 번호·동일한 이름·동일한 비밀번호를 입력한다. 생성기 자체는 실행 파일이나 등록 파일을 수정하지 않는다. 등록 파일은 원본 MSET이 대상 DOS 파일시스템에서 생성하게 한다. 잘못된 번호는 기존 등록 파일을 삭제할 수 있으므로 작업 복사본에서 실행한다.

## MDIR.REG와 에뮬레이션 호환성

`MDIR.REG`는 685(`0x2AD`)바이트다. VV의 로더는 읽기 크기·`0x3039` 헤더·일부 필드의 XOR 관계·파일 검색 결과를 검사한다. 등록 파일을 다른 환경으로 단순 복사하는 것과 원본 MSET으로 해당 환경에서 생성하는 것은 동일하지 않다.

특히 VV는 DOS FindFirst의 DTA 비공개 영역 `0x0F/0x10`도 비교한다. DOSBox-X의 자료 구조는 이 위치를 디렉토리 클러스터 값으로 사용하며 FAT 이미지 드라이버는 이 값을 채운다. 일반 호스트 폴더 드라이버와는 경로가 다르다. [DTA 구조](https://github.com/joncampbell123/dosbox-x/blob/dosbox-x-v2026.10.01/include/dos_inc.h), [FAT 드라이버](https://github.com/joncampbell123/dosbox-x/blob/dosbox-x-v2026.10.01/src/dos/drive_fat.cpp).

실제 비교에서 동일한 동봉 후보를 사용해도 일반 폴더 마운트에서는 메인이 Registered이고 VV는 등록 오류를 냈다. FAT12 이미지 안에서 다시 등록하자 VV가 문서를 표시했다. 따라서 이전의 Register version only 메시지를 등록번호 부재만으로 설명할 수 없다. 이전 실행 기록은 당시 조건의 결과로 보존한다.

## 원본에서 생성 번호 검증

위 합성 입력으로 원본 MSET이 685바이트 MDIR.REG를 생성했다. SHA-256은 `8bda199ee72b9618e35cc68302042d72f02e30363d01158598b24a3e53959c60`이다. Mdir를 완전히 재시작한 뒤 정보 상자에서 `Registered to`와 `MDIR64BIT RESEARCH`를 확인했고, 별도 VV 실행에서도 ALPHA.TXT가 표시됐다. [정보 상자 문자 기록](evidence/2026-10-21/generated-about.txt), [VV 화면](evidence/2026-10-21/generated-vv.png), [검증 요약](evidence/2026-10-21/registration-verification.json).

대조 실험은 정상 이미지의 별도 복사본에서 마지막 그룹만 `0001`로 바꿨다. 입력 체크섬은 같지만 MSET 종료 후 MDIR.REG가 없었다. 초기에는 입력 체크섬만 충족하는 번호를 시도해 실패했고, 파일 생성 루틴을 추가 분석하여 두 번째 검사를 찾아 수정했다. 성공 판정은 입력 창 통과가 아니라 파일 생성·새 프로세스의 등록 표시·VV 실행으로 했다. 실제 원본 수용 검증은 위 한 세트이며, 모든 ASCII 입력 조합의 수용을 보증하지 않는다.

## 등록판 기능 관찰

- **VV**: 합성 ALPHA.TXT의 `alpha-original`이 실제 그래픽 화면에 표시됐다. 인코딩·한자·글꼴·줄바꿈·저장 각각의 전체 조합은 추가 조사 대상이다.
- **MF**: 0으로 채운 1.44MiB 가상 플로피 A:를 포맷했다. 종료 후 이미지의 `55AA` 부트 서명과 512바이트 섹터 설정을 확인했다. 실제 디스크는 사용하지 않았다.
- **MCOPY**: 작은 C: 이미지에서는 임시 공간 부족 오류가 발생했다. 충분한 공간의 FAT16/MBR 이미지에서 A: 읽기 완료 후 Write가 ON이 됐고, B:를 선택해 Format ON으로 쓰기를 완료했다. 종료 후 두 이미지가 바이트 단위로 동일했다. 두 이미지 모두 SHA-256 `c0090109f87740bd18ceec670967c08de2999facbada0d1bb017124728e357f0`이다. 실제 플로피 장치는 사용하지 않았다.

MF/MCOPY 실험에는 동봉 후보로 원본이 생성한 등록 파일을 사용했고, 새 생성 번호는 별도 FAT12 이미지에서 검증했다. 따라서 새 번호로 MF/MCOPY까지 반복 실행했다고 주장하지 않는다. VV의 인코딩·편집·저장, MF의 불량 섹터와 취소, MCOPY의 형식별 조합·오류·복수 사본은 남아 있다. 아래 후속 조사 순서에 따라 기존 기능 ID별 상태를 확장한다.

## 후속 조사 순서

1. VV의 긴 줄·탭·인코딩·보기 설정 저장을 독립 표본으로 확인했다. [2차 관찰 결과와 남은 항목](VV_RUNTIME_FINDINGS.ko.md)을 따른다. 검색·본문 저장은 확인된 원본 기능이 아니다.
2. 디렉토리 작업·주석 동반 처리·풀메모리의 일부 경로를 기존 ID에 연결했다. [후속 관찰과 미해결 사항](REGISTERED_OPERATIONS.ko.md)을 따른다.
3. MF/MCOPY의 초기 취소·오류·같은 용량 Format OFF를 조사했다. [후속 결과와 Quick 예외](DISK_RUNTIME_FINDINGS.ko.md)를 따르며 다른 용량·후기 취소는 남아 있다.
4. 압축 외부도구와 Win95 비교 환경의 차단 항목을 별도로 해결한다.
5. P0의 남은 판정을 정리한 후 P1 파일 포맷·Windows x64 아키텍처를 확정한다. 새 Windows판에 원본의 등록 제한이나 DOS 디렉토리 클러스터 의존을 승계할 필요는 없다.
